1. What Is ROS 2?

What you just saw is ROS 2 in action. ROS 2 (Robot Operating System 2) is a middleware framework that lets independent programs — running on different machines, written in different languages — share data over a network as if they were all in the same process.

Unlike ROS 1, ROS 2 is built on the DDS (Data Distribution Service) standard, giving it real-time capabilities, multi-robot support, and better security. The robot runs a collection of ROS 2 nodes continuously; your laptop can subscribe to any of their output topics over the Ethernet cable.

1.1 Core Concepts

Concept Description K1 Example
Node A single executable process with one responsibility. Camera driver, walk controller, IMU reader
Topic A named channel. Publishers push data; subscribers receive it. Asynchronous — sender doesn't wait for a reader. /booster_video_stream, /low_state
Message A typed data structure sent over a topic. sensor_msgs/CompressedImage, sensor_msgs/Imu
Service Request/response — caller blocks until the server replies. For discrete one-off actions. Query robot mode, trigger a behaviour
Action Like a service but streams feedback during long-running tasks. Navigate to a waypoint, execute a gait

3. FastDDS Configuration for Ethernet

By default, ROS 2 uses UDP multicast for peer discovery — one machine broadcasts "I'm here!" and all others on the network hear it. On a direct Ethernet cable or an unmanaged switch, multicast is often blocked and the two machines never find each other. FastDDS with a static peer list bypasses this entirely.

3.1 Create the FastDDS Configuration File

On your laptop, create ~/robots/k1/config/fastdds_k1.xml:

<?xml version="1.0" encoding="UTF-8" ?>
<profiles xmlns="http://www.eprosima.com/XMLSchemas/fastRTPS_Profiles">
  <transport_descriptors>
    <transport_descriptor>
      <transport_id>udp_transport</transport_id>
      <type>UDPv4</type>
    </transport_descriptor>
  </transport_descriptors>
  <participant profile_name="k1_participant" is_default_profile="true">
    <rtps>
      <userTransports>
        <transport_id>udp_transport</transport_id>
      </userTransports>
      <useBuiltinTransports>false</useBuiltinTransports>
      <builtin>
        <discovery_config>
          <initialPeersList>
            <locator><udpv4><address>192.168.10.102</address></udpv4></locator>
          </initialPeersList>
        </discovery_config>
      </builtin>
    </rtps>
  </participant>
</profiles>

3.2 Set Environment Variables

Add to your laptop's ~/.bashrc and run source ~/.bashrc:

# ROS 2 environment — add to ~/.bashrc on your laptop
source /opt/ros/humble/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export FASTRTPS_DEFAULT_PROFILES_FILE=~/robots/k1/config/fastdds_k1.xml

3.3 Why the XML File Is Needed (DDS vs WiFi Discovery)

ROS 2 DDS discovery broadcasts "participant announcement" UDP packets. On WiFi every device on the subnet hears the broadcast automatically. On a direct Ethernet cable or an unmanaged switch, multicast packets are often not forwarded — the two machines never discover each other and ros2 topic list returns nothing from your laptop.

The XML file hard-codes the robot's IP as an initial peer, so your laptop sends the discovery packet directly to 192.168.10.102 instead of multicasting. No multicast needed — discovery always works.

5. Live Data Challenge

Don't look these up — figure them out by exploring ros2 topic list, ros2 topic echo, and ros2 topic hz. Use ros2 interface show to understand message fields when you need to.

  1. Find the head orientation topic. The K1's head pose is published somewhere. Find the topic name, echo one message, and identify which field contains the yaw (left/right) angle. Hint: run ros2 topic list | grep head
  2. Measure the camera frame rate. Use ros2 topic hz on the camera topic and run it for 10 seconds. What is the actual publish rate? Is it stable or does it fluctuate? Record the min, max, and mean Hz.
  3. Count the robot's joints. Echo /joint_states once (--once flag) and count how many joint names are listed. Does the number match the advertised 22 DOF? If not, explain why some joints may be missing.
  4. Find a topic that changes when you move the robot's head. With the robot in damping mode, gently move the head by hand while watching topic data. Which topic values change? Which stay constant? List at least two topics that respond and two that don't.
  5. Find the walking state topic. There is a topic that tells you the robot's current locomotion mode (standing, walking, damping, etc.). Find it, echo it, and report the field name and value when the robot is in damping mode.
Useful trick: ros2 topic list | grep -i walk, ros2 topic list | grep -i state, and ros2 topic list | grep -i mode will narrow the search quickly.

6. Python Exercise — Writing a ROS 2 Subscriber Node

Reading data from the terminal is useful for debugging but eventually you want to write code that reacts to it. Here's your first ROS 2 Python node: it subscribes to the head pose topic and prints a plain-English description of where the robot's head is pointing.

6.1 head_reporter.py — Full Code with Explanation

#!/usr/bin/env python3
# head_reporter.py — prints head direction in plain English

import rclpy                          # ROS 2 Python client library
from rclpy.node import Node           # base class for all ROS 2 nodes
from geometry_msgs.msg import Pose    # message type for head_pose topic
import math

class HeadReporter(Node):
    def __init__(self):
        # Every node needs a unique name — used in rqt_graph
        super().__init__("head_reporter")

        # create_subscription(msg_type, topic, callback, queue_size)
        self.sub = self.create_subscription(
            Pose,
            "/head_pose",
            self.on_pose,      # called every time a message arrives
            10                 # keep at most 10 messages in the queue
        )
        self.last_report = ""  # avoid printing the same line repeatedly

    def on_pose(self, msg: Pose):
        # Extract yaw and pitch from the quaternion orientation
        q = msg.orientation
        # Convert quaternion → yaw (left/right) and pitch (up/down)
        yaw   = math.atan2(2*(q.w*q.z + q.x*q.y),
                            1 - 2*(q.y*q.y + q.z*q.z))
        pitch = math.asin(max(-1, min(1, 2*(q.w*q.y - q.z*q.x))))

        yaw_deg   = math.degrees(yaw)
        pitch_deg = math.degrees(pitch)

        # Map angles to plain English
        if   yaw_deg >  15:  horiz = "LEFT"
        elif yaw_deg < -15:  horiz = "RIGHT"
        else:                  horiz = "CENTER"

        if   pitch_deg >  10: vert = "UP"
        elif pitch_deg < -10: vert = "DOWN"
        else:                   vert = "LEVEL"

        report = f"Robot head is pointing {horiz} and {vert} " \
                 f"(yaw={yaw_deg:.1f}° pitch={pitch_deg:.1f}°)"

        # Only print when the direction actually changes
        if report != self.last_report:
            print(report)
            self.last_report = report

def main():
    rclpy.init()                       # start the ROS 2 runtime
    node = HeadReporter()
    try:
        rclpy.spin(node)               # loop forever, calling callbacks
    except KeyboardInterrupt:
        pass
    finally:
        node.destroy_node()
        rclpy.shutdown()

if __name__ == "__main__":
    main()

7. Break It On Purpose — Diagnosing DDS Failures

The best way to understand why the FastDDS XML file matters is to remove it and watch everything break. Do this deliberately in a controlled way — you'll remember it far better than any explanation.

  1. Confirm topics are visible. Run ros2 topic list — you should see the full K1 topic list.
  2. Switch to the wrong domain ID. In a new terminal (don't change your main terminal): 
    export ROS_DOMAIN_ID=1   # robot uses 0; this terminal now lives in a different universe
ros2 topic list
    Result: empty list. The robot's topics have vanished.
  3. Break the FastDDS XML path. In another new terminal: 
    export FASTRTPS_DEFAULT_PROFILES_FILE=/tmp/does_not_exist.xml
ros2 topic list
    Result: empty list (or a warning then empty). Without the static peer address, your laptop falls back to multicast discovery which fails on the direct Ethernet link.
  4. Fix it and verify recovery. Open a fresh terminal (inherits the correct ~/.bashrc) and run ros2 topic list again — topics reappear immediately.
  5. Document the failure modes. Take a screenshot of each broken state and the corrected state.
⚠ Only break it in a new terminal — the environment variable change only affects that shell session. Your main working terminal is unaffected. Never export the wrong values in the terminal you're actively using for robot commands.

7.1 DDS Failure Modes Summary

Symptom Most Likely Cause Fix
ros2 topic list is empty Wrong ROS_DOMAIN_ID, missing XML file, or wrong IP in XML echo $ROS_DOMAIN_ID (must be 0); check $FASTRTPS_DEFAULT_PROFILES_FILE exists
Topics appear from robot but not laptop's own nodes Firewall blocking DDS ports (7400–7500 UDP) sudo ufw allow 7400:7500/udp
Topics visible but echo shows no data QoS mismatch (robot publishes Best Effort; subscriber expects Reliable) ros2 topic echo --qos-reliability best_effort /topic
Intermittent data drops High CPU on Jetson or Ethernet cable issue Check ros2 topic hz for irregular timing; try a different cable

8. Recording and Playing Back Rosbags

Rosbag2 captures a snapshot of every topic to disk. You can replay it later as if the robot were live — invaluable for offline development when the robot isn't available. 

# Record all topics for 10 seconds
ros2 bag record -o k1_test --duration 10 -a

# See what was captured
ros2 bag info k1_test

# Replay at normal speed (topics republish as if live)
ros2 bag play k1_test

# Replay at half speed — useful for debugging fast events
ros2 bag play k1_test --rate 0.5

# Record only the sensors you care about (saves disk space)
ros2 bag record -o k1_sensors \
    /booster_video_stream \
    /robot_interface/imu \
    /low_state
Tip: The camera topic alone generates ~2–5 MB/s. A 10-second full recording can be 50–100 MB. Always record only the topics you need, or use --duration to limit the time.
